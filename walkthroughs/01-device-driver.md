# Build a device driver and discovery loop

The public plugin has one `example_device` module type with `example_read` and `example_write` task types. Open `engine/include/example_device_module.h`, `engine/src/example_device_driver.cpp`, and `engine/src/example_device_discovery.cpp` in that plugin source. This workspace keeps rocket-themed channel names to illustrate a control application; it does not require another plugin device type.

1. Start the workspace using [Start](../README.md#start). Open **Modules -> example_device_1** and the `example_device_read` and `example_device_write` tasks. Both select that module. The read table maps sensor and sample-health fields to output channels. The write table maps coil and igniter commands to input channels with matching `_state` readbacks. The module creates the four `rocket_sim_fault_*` controls and `rocket_sim_run_fill`; the read task consumes them as simulation inputs. Module connection follows the configured prefix and remains visible even when the read task is stopped.
2. In `on_configure`, validate the bindings, create fixed channels, and retain their handles with the module in `TaskRuntime` context. The read callback publishes sensor data; the write callback reads mapped commands and publishes their applied state readbacks. The simulated module uses a local mutex because the two tasks share it. To try a remap, create a channel named `rocket_sim_extra_flow`, change only the `flow` row in the read task, save, and compare it with the other measurements. Restore `rocket_sim_flow` before running the sequence.
3. Run the sequence. Compare `rocket_sim_fuel_request`, `rocket_sim_fuel_open_coil`, and `rocket_sim_fuel_state`. After the half-second open pulse ends, the valve state stays at `1`; after a close pulse it stays at `0`. This is the last-known state, not measured position feedback.
4. Open **Logs** and filter the **Example device** stream for task lifecycle messages. Observe commands, coil states, DCode's retained valve states, connection, and sample validity in Channels. Normal read/write cycles do not emit logs. The write task's `on_end` de-energizes outputs and clears its state readbacks.

The discovery loop runs at 1 Hz. It advertises the simulated endpoint whenever no example device is configured; replace that check with your device probe. It suppresses offers when an example-device module is already configured, refreshes a presence lease, respects engine-scoped muting, and withdraws stale offers through `dartwic.module-discovery`. Provisioning supplies the module type, read/write task types, and explicit binding tables, as the Modbus plugin does.

Inject **DISCONNECT DEVICE**. Device validity becomes 0 and outputs de-energize. Clear it and observe valid samples again. To try provisioning itself, stop/delete the two driver tasks and module in a disposable copy, then accept the discovery notification. Select the discovered module in the generated task editors. Restore the original workspace copy afterward.

[Record and review](../README.md#operate-and-record) the failure and recovery. Compare channel timestamps to explain the delay between a request and feedback.
