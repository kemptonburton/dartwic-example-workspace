# Build a device driver and discovery loop

The public plugin has one `example_device` module type with `example_read` and `example_write` task types. Open `engine/include/example_device_module.h`, `engine/src/example_device_driver.cpp`, and `engine/src/example_device_discovery.cpp` in that plugin source. This workspace keeps rocket-themed channel names to illustrate a control application; it does not require another plugin device type.

1. Start the workspace using [Start](../README.md#start). Open **Modules -> example_device_1** and the `example_device_read` and `example_device_write` tasks. Both select that module. Their binding tables map each device field directly to a state channel. The read table maps measurements and applied feedback to output channels; the write table maps command channels to coil and igniter fields. The `rocket_sim` prefix names fault controls and the DCode ox-tank input. Module connection follows the configured prefix and remains visible even when the read task is stopped.
2. In `on_configure`, validate the bindings, create fixed channels, and retain their handles with the module in `TaskRuntime` context. The read callback publishes mapped device state; the write callback reads mapped commands. The simulated module uses a local mutex because the two tasks share it. To try a remap, create a channel named `rocket_sim_extra_flow`, change only the `flow` row in the read task, save, and compare it with the other measurements. Restore `rocket_sim_flow` before running the sequence.
3. Run the sequence. Compare `rocket_sim_fuel_request`, `rocket_sim_fuel_open_coil`, `rocket_sim_fuel_open_applied`, and `rocket_sim_fuel_position`. A requested operation is not proof of its applied output or measured position.
4. Open **Logs** and filter the **Example device** stream for task lifecycle messages. Observe commands, applied outputs, positions, connection, and sample validity in Channels. Normal read/write cycles do not emit logs. The write task's `on_end` de-energizes outputs.

The discovery loop runs at 1 Hz. Its endpoint check is a simulated presence flag; replace that check with your device probe. It suppresses offers when an example-device module is already configured, refreshes a presence lease, respects engine-scoped muting, and withdraws stale offers through `dartwic.module-discovery`. Provisioning supplies the module type, read/write task types, and explicit binding tables, as the Modbus plugin does.

Inject **DISCONNECT DEVICE**. Device validity becomes 0 and outputs de-energize. Clear it and observe valid samples again. To try provisioning itself, stop/delete the two driver tasks and module in a disposable copy, then accept the discovery notification. Select the discovered module in the generated task editors. Restore the original workspace copy afterward.

[Record and review](../README.md#operate-and-record) the failure and recovery. Compare channel timestamps to explain the delay between a request and feedback.
